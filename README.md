# ICT Tech Lab server

One Node.js service that serves the game and stores accounts, progress, and certificates in PostgreSQL.

## Files
- `server.js`: API and static file server
- `db.js`: database layer (PostgreSQL, plus an in-memory store for tests only)
- `schema.sql`: tables, all named `ict_*` so another site can share the database
- `render.yaml`: Render blueprint that creates the database and the web service
- `public/index.html`: the game (ICT Tech Lab v6)
- `test/api-test.js`: API tests (`npm test`)

## Deploy on Render
1. Create a GitHub repo and upload everything in this folder.
2. In Render, choose New > Blueprint and select the repo. This creates `ict-tech-lab-db` and `ict-tech-lab`.
3. Open the web service URL when it finishes building.

Free-plan limits: the database expires 30 days after creation unless you upgrade it, and the free web service sleeps after about 15 minutes without visitors, so the first load after a pause is slow.

## Second site on the same database
Give the other site the database's Internal Database URL as `DATABASE_URL`. Use a different table prefix (not `ict_`) so the tables don't clash.

## API
- `POST /api/signup` `{username, password}`: returns `{token, username}`
- `POST /api/login` `{username, password}`: returns `{token, username}`
- `POST /api/logout`: ends the session
- `GET /api/progress`, `PUT /api/progress` `{data}`: load or save progress (Bearer token)
- `POST /api/certificates` `{program: "coc1"}`: issues a certificate once every module in that program is complete (Bearer token)
- `GET /api/certificates/ICT-XXXXXXXXXXXX`: public check that a certificate is genuine

## Password security
- Passwords are mixed with a secret pepper (`PASSWORD_PEPPER`, generated by Render and kept out of the database), then hashed with scrypt and a unique salt per user.
- Login attempts are limited to 10 failures per username and 50 per network address in 15 minutes. Sign-ups are limited to 100 per network per hour.
- Passwords must be 8 to 128 characters, cannot be common passwords, and cannot contain the username.
- Keep `PASSWORD_PEPPER` safe. Changing it makes every existing password stop working.
- Limits are kept in memory, so they reset on restart and apply per running instance. Use one instance, or move them to the database if you scale out.

## Limitations
- The game still saves progress in each browser. It needs changes to call these endpoints. Those changes aren't included here.
- The server trusts the progress the browser sends, so a determined student could still submit fake progress. Real verification needs the server to record each module result itself.
- Set `PGSSL=require` only when connecting from outside Render. Internal URLs don't need it.
